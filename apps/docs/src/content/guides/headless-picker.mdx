## What the driver owns

`@pbroom/color-kit/driver` is a picker without a view: pure functions over a
[`ColorState`](/api/driver/color-state#ColorState), plus the geometry, keyboard and
pointer models a picker needs. `@pbroom/color-kit/react` is one binding built on it.
The example on this page is another, in plain DOM code, so it works under any
framework.

## State

[`createColorState`](/api/driver/color-state#createColorState) builds the state from a
requested color: the request, its sRGB and Display P3 mappings, the active
gamut and view, and out-of-gamut flags. Four reducers update it:
[`setColorRequested`](/api/driver/color-state#setColorRequested),
[`setColorChannel`](/api/driver/color-state#setColorChannel),
[`setColorActiveGamut`](/api/driver/color-state#setColorActiveGamut) and
[`setColorActiveView`](/api/driver/color-state#setColorActiveView). Each returns the same
object for a no-op, so `next === state` is enough to skip a render.
`createColorState` and `setColorActiveGamut` take the gamut as a string, a
`DisplayGamut`: `'srgb'` or `'display-p3'`. Anything else, `'p3'` and
`'rec2020'` included, throws a `TypeError`. Picker state names the gamut a
color is shown in; core's gamut and plane queries take an imported
[`Gamut`](/api/plane/gamut#Gamut) object instead (see
[Gamut and tolerance](/concepts/gamut-and-tolerance#gamuts-are-imported-objects)).

```ts title="state.ts"
import { parse, toHex } from '@pbroom/color-kit';
import { createColorState, setColorChannel } from '@pbroom/color-kit/driver';

const state = createColorState(parse('#3b82f6'));
const next = setColorChannel(state, 'l', 0.4, 'user');
toHex(next.requested); // → '#003baa'
setColorChannel(next, 'l', 0.4, 'user') === next; // → true
```

## Geometry

A 2D area maps two OKLCH channels to a rectangle.
[`resolveColorAreaAxes`](/api/driver/color-area#resolveColorAreaAxes) defaults to
lightness on `x` and chroma on `y`. Pointer input goes through
[`normalizeColorAreaPointer`](/api/driver/color-area#normalizeColorAreaPointer) (client
pixels to clamped `[0, 1]`, `y` down) and
[`colorFromColorAreaPosition`](/api/driver/color-area#colorFromColorAreaPosition);
[`getColorAreaThumbPosition`](/api/driver/color-area#getColorAreaThumbPosition) goes
back. Sliders have the same trio:
[`normalizeColorSliderPointer`](/api/driver/color-slider#normalizeColorSliderPointer),
[`colorFromColorSliderPosition`](/api/driver/color-slider#colorFromColorSliderPosition) and
[`getColorSliderThumbPosition`](/api/driver/color-slider#getColorSliderThumbPosition).

## Keyboard and ARIA

[`colorFromColorAreaKey`](/api/driver/color-area#colorFromColorAreaKey) and
[`colorFromColorSliderKey`](/api/driver/color-slider#colorFromColorSliderKey) implement
arrows, Page Up/Down and Home/End, wrapping hue and clamping the rest. They
return `null` for keys they do not handle, so call `preventDefault` only when
they return a color. [`getColorAreaValueText`](/api/driver/color-area#getColorAreaValueText)
and [`getColorSliderValueText`](/api/driver/color-slider#getColorSliderValueText) produce
`aria-valuetext` such as `Lightness 60%, Chroma 0.1` and `Hue 213°`. A
slider exposes one number, so the area thumb sets `aria-valuenow`,
`aria-valuemin` and `aria-valuemax` from the x axis and
`aria-roledescription="2D slider"`; the value text names both axes.

## Drag throttling

[`createPointerDragController`](/api/driver/drag-controller#createPointerDragController)
commits `start` and `end` immediately and coalesces moves to at most one
commit per animation frame. Moves within `dragEpsilon` (default `0.0005`) are
skipped and commits are capped at `maxUpdateHz` (default 60); a rate-limited
point is retried on the next frame, never dropped. Pass a frame scheduler as
the second argument to drive drags deterministically in tests.

The controller tracks one drag, not one pointer. The binding records the
`pointerId` that started the drag, captures it, and ignores other pointers
until that one lifts or is cancelled, so a second finger cannot steer or end
the drag.

## Channel fields

A number field for one channel needs four things from the driver.
[`getColorChannelValue`](/api/driver/color-channel#getColorChannelValue) reads a
channel of the color in OKLCH, RGB or HSL, and
[`formatColorChannelValue`](/api/driver/color-channel#formatColorChannelValue) turns it
into the field's text. On commit,
[`normalizeColorChannelValue`](/api/driver/color-channel#normalizeColorChannelValue)
clamps the typed number into the channel's range, or wraps it for a hue, and
[`colorFromColorChannelValue`](/api/driver/color-channel#colorFromColorChannelValue)
writes it back.
[`resolveColorChannelRange`](/api/driver/color-channel#resolveColorChannelRange),
[`resolveColorChannelWrap`](/api/driver/color-channel#resolveColorChannelWrap),
[`resolveColorChannelSteps`](/api/driver/color-channel#resolveColorChannelSteps) and
[`getColorChannelLabel`](/api/driver/color-channel#getColorChannelLabel) supply each
channel's defaults: its range, whether it wraps, its step sizes and its
accessible label.

```ts title="channel-field.ts"
import { parse, toHex } from '@pbroom/color-kit';
import {
  colorFromColorChannelValue,
  formatColorChannelValue,
  getColorChannelValue,
  normalizeColorChannelValue,
  resolveColorChannelRange,
  resolveColorChannelWrap,
} from '@pbroom/color-kit/driver';

const blue = parse('#3b82f6');

// The field's text: the color's red channel, 0-255.
formatColorChannelValue(getColorChannelValue(blue, 'rgb', 'r'), 0); // → '59'

// Commit what was typed: clamp it into the range, then write it back.
const range = resolveColorChannelRange('rgb', 'r'); // → [0, 255]
const wrap = resolveColorChannelWrap('rgb', 'r'); // → false
const red = normalizeColorChannelValue(Number('300'), range, wrap); // → 255
toHex(colorFromColorChannelValue(blue, 'rgb', 'r', red)); // → '#ff82f6'

// A hue wraps instead of clamping.
const hueWraps = resolveColorChannelWrap('hsl', 'h'); // → true
normalizeColorChannelValue(400, [0, 360], hueWraps); // → 40
```

An RGB or HSL edit that lands on a gray keeps the color's OKLCH hue, and the
HSL hue of a gray reads back as that stored hue, not `0`. Parsing math
expressions and scrubbing a value by dragging are generic number-field
behavior and belong to a component library such as
[control-kit](https://github.com/pbroom/control-kit), not to the driver.

## Painting

[`getSliderGradientStyles`](/api/driver/slider-gradient#getSliderGradientStyles) returns
`linear-gradient()` strings for a rail, in Display P3 by default with an sRGB
fallback. [`getColorDisplayStyles`](/api/driver/color-state#getColorDisplayStyles) returns
a `background` and `backgroundColor` pair: P3 where the browser supports it,
sRGB underneath. For overlays,
[`getColorAreaGamutBoundaryPoints`](/api/driver/color-area#getColorAreaGamutBoundaryPoints)
and
[`getColorAreaContrastRegionPaths`](/api/driver/color-area#getColorAreaContrastRegionPaths)
return plane geometry in area coordinates.

# Multi-Color State

`useMultiColor` manages named color collections (palette entries, gradient stops) with shared display configuration.

```tsx
import { useMultiColor } from 'color-kit/react';

export function Palette() {
  const colors = useMultiColor({
    defaultColors: {
      base: '#3b82f6',
      accent: 'oklch(0.8 0.4 145)',
    },
    defaultSelectedId: 'base',
  });

  return (
    <>
      <button onClick={() => colors.select('accent')}>Select accent</button>
      <button onClick={() => colors.setActiveGamut('srgb')}>
        Preview sRGB
      </button>
      <button
        onClick={() =>
          colors.setChannel('accent', 'h', 210, { interaction: 'user' })
        }
      >
        Shift accent hue
      </button>
    </>
  );
}
```

## Key API

- `state.colors[id]`: full `ColorState` per entry
- `setRequested(id, requested, options?)`: pass `explicitHue: false` for a
  color converted from hex, RGB, HSL or HSV, so an achromatic one keeps the
  entry's hue (see React Primitives, "Hue of achromatic colors")
- `setChannel(id, channel, value, options?)`
- `setActiveGamut(gamut)` / `setActiveView(view)`
- `addColor(id, color)` / `removeColor(id)` / `renameColor(id, nextId)`
- `select(id)`

## Controlled mode and `onChange`

Pass `state` and `onChange` to own the collection yourself. `onChange` fires synchronously inside the operation call, before React re-renders, in both controlled and uncontrolled modes, and is skipped for no-op operations.

Several operations in one tick compose: each `event.next` builds on the previous one, even before your new `state` prop arrives. After React re-renders, the `state` you committed becomes the base for later operations, so an update you ignore (by not passing it back) is not carried into the next one.

```tsx
const [state, setState] = useState(initialState);
const colors = useMultiColor({
  state,
  onChange: (event) => setState(event.next),
});

// Both edits land, in order.
colors.setChannel('base', 'l', 0.4);
colors.setChannel('accent', 'h', 210);
```
